## Часть 2. Демонстрация PICT: модель, ограничения, генерация (00:10–00:25)

Попарное тестирование (pairwise testing) — техника, при которой набор строится так, чтобы каждая пара значений любых двух параметров встретилась хотя бы в одном тест-кейсе. На практике такой набор получают инструментом.

### Цикл работы с PICT

```text
pict /?
pict model.txt > cases.txt
```

Инструмент принимает текстовую модель — параметры и их значения — и выдаёт набор строк с покрытием всех пар. Каждая строка становится заготовкой тест-кейса.

### Требования к модели

- не менее шести параметров;
- по два–четыре значения на параметр;
- обязательные ограничения модели (constraints);
- на выходе — покрытие каждой пары значений.

### Пример модели для сервиса авторизации

```text
card_status:        ACTIVE, INACTIVE, BLOCKED, EXPIRED
amount_vs_daily:    below, equal, above
amount_vs_monthly:  below, equal, above
amount_vs_balance:  below, equal, above
expiry:             valid, current_month, expired
terminal_type:      pos, atm, ecom
mcc:                grocery, restaurant, electronics, travel

# Ограничения
IF [card_status] <> "ACTIVE" THEN [amount_vs_daily] = "below"
    AND [amount_vs_monthly] = "below" AND [amount_vs_balance] = "below";
IF [expiry] = "expired" THEN [amount_vs_balance] = "below";
```

Полный перебор для этой модели составляет 4 × 3 × 3 × 3 × 3 × 3 × 4 = **3888** комбинаций. Попарный набор покрывает все пары значений при кратном сокращении числа строк.

### Ограничения техники

Покрытие всех пар не гарантирует полноты: взаимодействия трёх и более параметров остаются непроверенными. Критичные сочетания, известные команде, добавляются в набор вручную. Ограничения модели исключают невозможные сочетания — например, при неактивной карте лимиты и баланс не проверяются.

## Часть 3. Проектный слой: стратегия и план СМП (00:25–00:45)

### Тестовая стратегия СМП

Тестовая стратегия — долгосрочное описание подхода к тестированию на уровне системы. Она отвечает на два вопроса: почему тестирование организовано именно так и почему часть проверок осознанно исключена из области тестирования.

Стратегия составляется на всю систему и содержит:

- цель тестирования;
- уровни проверок и их обоснование;
- подход к приоритизации (риск-ориентированный);
- область тестирования и то, что осознанно оставлено вне её, с указанием основания.

Объём — 2–3 абзаца и перечень уровней проверок.

### Тестовый план СМП

Тестовый план описывает, как, кем и когда выполняются проверки. Обязательные разделы:

- область тестирования и подход;
- критерии входа и выхода;
- критерии приостановки и возобновления;
- ресурсы, расписание, риски и метрики.

Требуется структура, а не объём. Критерий выхода формулируется в измеримых терминах, например: отсутствие открытых дефектов критического и высокого уровней при достигнутом целевом покрытии.

> **Ориентир**: формулировки разделов и уровень детализации разобраны на лекции 3 в слайдах «Тестовая стратегия: сквозной пример» и «Тестовый план» (`slides/module-02/lecture-03.md`).

## Часть 4. Ядро: классы эквивалентности, границы, pairwise (00:45–01:10)

Ядро — Authorization и Card-Management. Для них применяется полный набор техник лекции 3.

### Классы эквивалентности

Класс эквивалентности — множество входных значений, которые система обрабатывает одинаково. Методика:

1. выделить классы по каждому полю;
2. создать тест-кейс на каждый класс — минимум один представитель.

Правила:

- позитивные и негативные классы выделяются раздельно;
- один невалидный класс — один тест-кейс; смешивать невалидные значения нельзя.

Примеры для Authorization и Card-Management: статус карты (ACTIVE, INACTIVE, BLOCKED, EXPIRED), сумма транзакции относительно лимитов и баланса, корректность PAN, формат `expiryDate`.

### Граничные значения

Граничные значения (boundary value analysis, BVA) — техника, при которой данные выбираются на границах классов и рядом с ними.

- **ON** — значение ровно на границе;
- **OFF** — значение непосредственно за границей.

Для каждой границы берутся три точки: значение на границе, ниже и выше неё. Для Authorization ключевые границы: `dailyLimit`, `monthlyLimit`, `availableBalance`, `expiryDate` (MMYY). Для Card-Management — длина и корректность PAN, формат `expiryDate`.

> **Ориентир**: методика и примеры — на лекции 3, слайды «Граничные значения: методика» и «Граничные значения: пример» (`slides/module-02/lecture-03.md`).

### Попарное тестирование

Для ядра строится модель PICT (см. Часть 2), задаются ограничения и генерируется набор. Каждая строка набора проецируется в отдельный тест-кейс.

### Реестр тест-кейсов и трассировка

Каждый тест-кейс фиксирует:

- идентификатор и связанное требование;
- вид: позитивный или негативный;
- предусловие, шаги, ожидаемый результат;
- источник: класс, граница или строка попарного набора.

Правила: несколько валидных значений допустимо объединять в один кейс, несколько невалидных — нельзя. Трассировка «требование → тест-кейс → техника» связывает документацию с требованиями.

## Часть 5. Периферия: чек-листы на остальные сервисы (01:10–01:22)

Чек-лист — упорядоченный перечень проверок, определяющий, что подлежит проверке, без конкретных входных данных, шагов и ожидаемых результатов.

Подготовьте два перечня:

- **дымовое тестирование** — быстрая оценка работоспособности системы после сборки;
- **критический путь** — проверка ключевых пользовательских сценариев процессинговой цепочки.

Для периферийных сервисов (Gateway, Switch, симуляторы, Transaction Logger, Web Dashboard) достаточно классов верхнего уровня и чек-листов: их поведение проще, а глубокая модель не даёт соразмерного эффекта. Такой подход соответствует риск-ориентированному тестированию: объём работ следует за риском.

## Часть 6. Самопроверка по чек-листу и разбор проблем (01:22–01:30)

### Лист самопроверки

Пройдите перед сдачей, отмечая выполненные пункты:

- [ ] Стратегия и тестовый план составлены на всю систему, а не на один сервис
- [ ] Для Authorization и Card-Management выделены классы эквивалентности с представителями
- [ ] Границы заданы тройками ON/OFF для лимитов, баланса и `expiryDate`
- [ ] Модель PICT содержит не менее шести параметров и ограничения
- [ ] Попарный набор сгенерирован и спроецирован в тест-кейсы
- [ ] Подготовлены чек-листы дымового тестирования и критического пути
- [ ] Выполнена трассировка «требование → тест-кейс»

### Типичные ошибки

| Ошибка | Следствие |
|---|---|
| Модель без ограничений | Генератор включает невозможные сочетания — набор непригоден |
| Покрытие пар как гарантия полноты | Критичные тройки не покрыты и не добавлены вручную |
| Документация на один сервис | Проектные стратегия и план отсутствуют |
| Смешивание невалидных значений | Невозможно локализовать причину отказа |
